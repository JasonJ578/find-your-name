## 1. 项目形态与技术方案

### 1.1 最终形态

玩家打开一个网址，看到一个虚构的社交平台。点帖子、点链接、进不同页面，从文字里找线索。最后在"指认页"把线索拖到板上，系统判断线索够不够，给出不同结局。

### 1.2 技术形态（一句话）

**一堆静态网页 + 一份公共样式 + 几个公共脚本。** 不需要服务器，不需要数据库，不需要前端框架。

理由：

- 10–30 页，规模小，框架带来的好处抵不上学习成本。
- 四个人都不是专业前端，纯 HTML 最容易看懂、最容易让 AI 改。
- 部署就是复制文件，GitHub Pages 免费。
- 出问题能直接定位到某一个文件。

### 1.3 两类页面：流式页 vs 画布页

这是全手册最重要的一节。

**流式页（像 Word 文档）**

元素一个接一个往下排，位置是"相对的"。窗口变窄，文字自动换行，下面的内容自动往下让。内容多长都能装下，装不下就滚动。

适合：微博信息流、帖子详情、评论区、新闻正文、聊天记录、登录页。

**画布页（像 PPT 的一页）**

每个元素有固定坐标，你把它放在哪就钉在哪。窗口变大变小，整页等比缩放，元素之间的相对位置不变。

适合：封面、标题页、案发现场全景、结局插画、证据板。

**为什么不能在同一页里随便混**

1. **文字会溢出。** 画布里的文本框高度是固定的。你按 3 行设计，队友多写 2 行，就会压住下面的按钮。流式页不会，下面的内容会自动让开。
2. **字号会跟着窗口缩小。** 画布整体缩放，字也缩。窗口小一点，12 号字变 8 号，看不清。流式页的字号是固定的。
3. **一页里两种缩放规则，接缝处对不齐。** 一半在缩、一半不缩，视觉上"打架"。
4. **窄窗口最惨。** 画布缩得太小，字全糊；流式页还能正常读。
5. **维护成本不同。** 画布页改一句话要重新调位置；流式页加一条评论只是加一段。四个人两种习惯，最后统一很痛苦。

**安全的混用方式**

- 每页先定一个主模式：`flow`（流式）或 `canvas`（画布）。
- 画布只作为一个"块"嵌在流式页里，有固定宽高比（比如 16:9），整块缩放，不参与文字排版。
- 画布块里尽量少放会变长的文字；必须放，就留足余量。
- 页面开头用注释标明模式，AI 按标注生成。

**两条判断规则**

1. 这页的内容会越加越多吗？会 → 流式。
2. 这页需要滚动吗？需要 → 流式。

两条都是"否"，才可以用画布。

**你的页面怎么分**

| 页面 | 模式 | 理由 |
|---|---|---|
| 入口 / 封面 | 画布 | 一张定死的画面，一屏看完 |
| 微博信息流 | 流式 | 帖子长短不一，要滚动 |
| 单条帖子 + 评论 | 流式 | 评论数量不定 |
| 个人主页 | 流式，头部可嵌画布块 | 头部构图固定，下面列表动态 |
| 新闻正文 | 流式 | 文字长 |
| 聊天记录 | 流式 | 消息条数不定 |
| 登录 / 密码页 | 流式 | 一张居中卡片就够 |
| 案发现场 / 线索图 | 流式页里嵌画布块 | 底图固定比例，热点按百分比定位 |
| 结局指认页 | 流式为主，线索板是画布块 | 线索数量不定，板子构图固定 |

**结论：九成页面是流式，画布只用在"一张定死的画面"上。** 这样你仍然可以在封面、现场、结局页享受"随便摆"，但不会在信息流页被文字撑爆。

### 1.4 目录约定

```
/
├── index.html                  入口 / 封面
├── 404.html                    假 404（以后想用再用）
├── weibo/
│   ├── index.html              平台首页（信息流）
│   ├── post-01.html            帖子详情
│   └── profile-01.html         个人主页
├── news/
│   └── index.html
├── chat/
│   └── index.html
├── ending/
│   └── index.html              指认页
├── assets/
│   ├── css/
│   │   ├── theme.css           颜色、字号、间距（全站唯一）
│   │   └── layout.css          页头页脚、栅格、通用组件
│   ├── js/
│   │   ├── state.js            进度存档
│   │   └── game.js             线索、结局判定
│   └── img/
│       ├── common/             公共图
│       └── weibo/              按页面分
└── docs/
    └── 开发方案与操作手册.md
```

规则：

- 路径用**英文小写 + 连字符**，内容用中文。
- 一个页面一个 HTML 文件。
- 每个页面文件夹只放自己的图片，公共图片放 `assets/img/common/`。

### 1.5 三条铁律

1. **一个页面一个 HTML 文件。**
2. **颜色、字号、间距只写在 `assets/css/theme.css`，页面里不写死。**
3. **需要交互的元素有固定名字**（用 `data-*` 属性），名字由 AI 定，人不在编辑器里改。

这三条是四个人能合到一起的基础，比任何工具都重要。

### 1.6 公共文件各自管什么

| 文件 | 管什么 | 谁能改 |
|---|---|---|
| `theme.css` | 颜色、字号、圆角、间距、阴影 | 指定一个人，改前打招呼 |
| `layout.css` | 页头、页脚、导航、栅格、通用卡片 | 指定一个人 |
| `state.js` | 存进度、读进度、加线索、查线索 | 只由 AI 改，人不手改 |
| `game.js` | 结局判定、指认页拖拽逻辑 | 只由 AI 改，人不手改 |

### 1.7 状态与结局怎么实现（说人话）

- 进度存在玩家自己的浏览器里（localStorage），关掉再开还在。
- `state.js` 只做四件事：记一个旗标、查一个旗标、加一条线索、查有没有某条线索。
- 所有页面只通过它读写，不直接碰浏览器存储。
- 结局判定：每个结局配一个"必需线索清单"，玩家提交时比对。缺一条就进不了完美结局。
- 指认页的拖拽：线索是积木，拖到板上；提交时把板上的线索和清单比对。这是脚本，不是排版。
- 玩家清空浏览器缓存，进度就没了。所以首页要放"重置进度"，另外做一个 `debug.html`（不对外链接），能直接给自己发线索，方便四个人测试。

### 1.8 素材规范

- 图片统一 WebP，宽度不超过 1600，单张小于 300KB。
- 头像 200×200 足够。
- 用系统字体，不引入中文字体文件（一个字体动辄好几 MB）。
- 图标用内联 SVG，不引图标库。
- 音频可选，单个控制在 1MB 内，必须由玩家点击后播放。

### 1.9 部署

GitHub Pages，公开仓库，免费。推上去 1 分钟内更新，网址形如：

```
https://<你的用户名>.github.io/find-your-name/
```

## 2. 工作流：AI 生成 → 人工微调 → 提交

### 2.1 每页的标准循环

1. 写"页面需求单"（模板见附录 B）。
2. 把**样板页 + 项目约定 + 需求单**一起发给 AI。
3. AI 输出一页完整的 HTML。
4. 本地用 Live Server 打开看。
5. 微调：改文字、换图、调间距、调位置。
6. **Commit（提交）。**
7. 下一轮只让 AI 改"指定部分"，不让它重写整页。

**第 6 步是关键。** 一定要在微调之后、下一次让 AI 动手之前提交。否则 AI 重写整页，你的手工修改就没了。

### 2.2 这种工作流会遇到的 8 个问题

1. **AI 重写整页，覆盖你的手工修改。**
   对策：微调后立刻 commit；让 AI"只改这一段"，并且让它输出完整文件，你对比后再替换。

2. **AI 不知道别的页长什么样，风格会飘。**
   对策：每次附上样板页的 HTML 和 `theme.css`，并说"沿用样板页的结构和类名"。

3. **AI 编造不存在的图片、链接、页面。**
   对策：先把素材文件建好（哪怕先是占位图），只让它引用已存在的文件名；链接目标页面先建空页。

4. **AI 写的脚本互相打架（变量重名、重复绑定事件）。**
   对策：每页脚本包在独立作用域里；状态只走 `state.js`；公共逻辑放 `game.js`。

5. **对话太长之后 AI 忘约定。**
   对策：一页一个对话；每次开头贴一段"项目约定"（1.5 的三条 + 命名规则）。

6. **响应式和绝对定位混在一页里打架。**
   对策：按 1.3 分类，一页只选一种主模式。

7. **四个人做出来四种风格。**
   对策：样板页 + 只用 `theme.css` 里的变量，不许写行内颜色。

8. **图片太大，页面加载慢、仓库爆炸。**
   对策：统一 WebP、限宽 1600、单张 300KB 以内。

### 2.3 微调工具怎么选

先用 **HTML Workbench** 和 **42 HTML Visual Editor** 各试十分钟，按这个测试：

1. 让 AI 生成一个带几个方块的测试页。
2. 用工具打开，把方块拖到别的位置。
3. 保存，刷新，看方块是不是真的动了。
4. 再保存一次、什么都不改，看 Git 里有没有多出"假改动"。
5. 看它有没有把元素的 `data-*` 名字改掉。

第 4 条最关键：有些编辑器一保存就整页重排，Git 里看起来全变了，四个人根本没法合并。

三个工具都不行时的兜底方案：

- 用浏览器 F12 直接改样式，把满意的数值记下来，让 AI 写回 `theme.css` 或页面。
- 慢一点，但绝不会破坏结构，也不会产生假 diff。
- 画布页（封面、结局）才考虑用 Figma / 即时设计画好再让 AI 转。
- 流式页（信息流、文章）不要用画布工具拖，拖完就不自适应了。

### 2.4 让 AI 稳定输出的四个技巧

1. **每次附样板页。** 只说"照这个风格"，比说十句形容词有用。
2. **一次只做一页。** 不要"顺便把另外两页也做了"。
3. **明确"不要做什么"。** 比如"不要引入外部库""不要写行内颜色""不要改导航"。
4. **让它输出完整文件，你对比后替换。** 不要让它直接改你磁盘上的文件，除非你刚 commit 过。

## 3. 线上 Git 仓库搭建（Windows / GitHub）

### 3.1 要装的东西

| 软件 | 用途 | 地址 |
|---|---|---|
| GitHub Desktop | 图形化 Git，不用敲命令 | https://desktop.github.com |
| VS Code | 编辑代码，自带预览插件 | https://code.visualstudio.com |
| VS Code 插件 Live Server | 本地起一个预览网址 | VS Code 扩展商店搜 "Live Server" |

### 3.2 注册 GitHub

1. 打开 https://github.com ，点 Sign up。
2. 邮箱、密码、用户名。**用户名会出现在网址里**，想好再定。
3. 验证邮箱。

### 3.3 安装并登录 GitHub Desktop

1. 安装后打开，选 "Sign in to GitHub.com"。
2. 浏览器里授权，回到桌面端。
3. 填名字和邮箱（会写进每次提交记录）。

### 3.4 把本地仓库发布到线上

你现在的情况是"本地已经是 Git 仓库，但没有线上地址"。

**图形界面（推荐）**

1. GitHub Desktop → 菜单 `File` → `Add local repository`。
2. 选择 `F:\Find Your Name`。
3. 如果提示"这不是一个 Git 仓库"，点它给的 `create a repository`。
4. 左上角 `Current Repository` 确认是 `Find Your Name`。
5. 点右上角 **Publish repository**。
6. Name 填 `find-your-name`（**不要有空格**）。
7. **取消勾选 `Keep this code private`**（要公开，Pages 才能免费用）。
8. 点 **Publish repository**。

**命令行（备选，你已经会跑命令）**

```powershell
cd "F:\Find Your Name"
git init
git add .
git commit -m "初始化"
git branch -M main
git remote add origin https://github.com/<你的用户名>/find-your-name.git
git push -u origin main
```

### 3.5 邀请另外三个人

1. 浏览器打开 `https://github.com/<你的用户名>/find-your-name`。
2. `Settings` → 左侧 `Collaborators` → `Add people`。
3. 输入他们的 GitHub 用户名，选权限 `Write`。
4. 他们去邮箱点接受。

### 3.6 另外三个人第一次拿到项目

1. 装 GitHub Desktop，登录自己的账号。
2. `File` → `Clone repository` → 选 `find-your-name`。
3. 本地路径选**不含中文和空格**的目录，例如 `D:\work\find-your-name`。
4. 点 `Clone`。

### 3.7 每天的三步：Pull / Commit / Push

四个人完全一样：

1. **开工前**：点上方 `Fetch origin`；如果有更新，点 `Pull origin`。
2. **改自己的页面**。
3. **收工前**：左下角 `Summary` 写清楚改了什么 → 点 `Commit to main` → 点 `Push origin`。

提交信息写法：

```
[微博] 首页：补充第 3 条评论的错字线索
[新闻] 正文：调整标题字号
[全局] theme.css：统一主色
```

**一天至少同步一次，不要攒一周。** 攒得越久，冲突越大。

### 3.8 冲突怎么办

- **现象**：Pull 的时候提示 conflict，文件里出现 `<<<<<<<` 这种东西。
- **原因**：两个人改了同一页的同一段。
- **处理**：不要硬合并。找一个人保留版本，另一个人把改动重新加一遍，然后 commit。
- **预防**：一个页面同一时间只归一个人；要改别人的页，先在群里说一声。

### 3.9 发布网址（GitHub Pages）

1. 仓库页面 → `Settings` → 左侧 `Pages`。
2. `Source` 选 `Deploy from a branch`。
3. `Branch` 选 `main`，目录选 `/ (root)`，点 `Save`。
4. 等 1–2 分钟，网址是：

```
https://<你的用户名>.github.io/find-your-name/
```

5. 以后每次 push，1 分钟左右自动更新。

每个文件夹里的 `index.html` 会自动变成 `.../weibo/` 这样的地址，正好符合"输入网址进入"的感觉。

**注意**：公开仓库 = 源码公开，玩家理论上能翻到谜底。前端游戏都这样，demo 阶段不用管；真介意的话，以后换私有仓库 + Cloudflare Pages。

### 3.10 Windows 上的几个坑

- **路径不要有中文和空格。** `F:\Find Your Name` 有空格，能跑，但偶尔出问题。建议以后把项目挪到 `F:\find-your-name`。
- **文件名用英文小写 + 连字符。** 中文文件名在 Git 和网址里容易出编码问题。
- **换行符**：Git 第一次提交可能提示 LF/CRLF，选默认即可。
- **不要提交**：`Thumbs.db`、`desktop.ini`、`*.psd`、`*.ai`、`node_modules`。在根目录建一个 `.gitignore`：

```
Thumbs.db
desktop.ini
.DS_Store
node_modules/
*.psd
*.ai
*.sketch
~$*
.vscode/
```

- **仓库别塞大图。** GitHub 单文件超过 100MB 会被拒，仓库超过 1GB 会警告。图片先压缩。

### 3.11 如果 GitHub 访问不稳定

- 开代理后再用 GitHub Desktop，通常就正常了。
- 或者用 Gitee：建仓库 → 邀请成员 → 推送方式一样。Gitee Pages 需要实名，审核较慢。
- 或者 GitHub 私有仓库 + Cloudflare Pages（免费，也能自定义域名，配置多几步）。

## 4. 四人协作一页纸（打印贴墙）

**页面归属表**（填好贴在群里）

| 成员 | 负责的页面 | 备注 |
|---|---|---|
| A | 微博线 5 页 | |
| B | 新闻线 5 页 | |
| C | 聊天线 5 页 | |
| D | 入口 + 结局 + 公共页 | 兼管 `theme.css` |

**七条规矩**

1. 一人一块页面，页面归属写清楚。
2. 动手前 Pull，收工前 Push。
3. 改别人的页，先在群里说一声。
4. `theme.css` 和 `layout.css` 只有一个人改。
5. 提交信息写"哪一页、改了什么"。
6. 遇到冲突不要慌，找负责人一起看。
7. 每周五一起玩一遍最新版。

**每周节奏**

- 周一 15 分钟：对齐本周做哪几页。
- 周五 30 分钟：合并、发布、一起试玩、记问题。

## 5. 六周排期

按每人每周 5–8 小时估算，可整体伸缩。

| 周 | 目标 | 产出 |
|---|---|---|
| W0 | 环境、仓库、样板页 | 四个人都能 Pull/Push；一张微博信息流样板页；项目约定短文档 |
| W1 | 入口 + 第一条线索链 | 入口页 + 3 页能连起来玩通的小链 |
| W2 | 各自页面初稿 | 每人 5 页左右，风格统一 |
| W3 | 线索串联 + 结局页 | 全局状态、指认页、至少 2 个结局 |
| W4 | 统一视觉 + 试玩 | 找 2 个外人试玩，记录卡点 |
| W5 | 修 bug + 发布 | 线上网址可玩，手机横向能看 |
| W6 | 缓冲 | 补内容、补美术、写说明 |

## 7. 常见问题

**Q：要不要用 React / Vue？**
不要。10–30 个静态页，纯 HTML 更简单，AI 也更容易改对。

**Q：要不要服务器和数据库？**
不要。进度存浏览器本地，密码在前端比对。这是 demo，不是上线产品。

**Q：能不能直接双击 HTML 打开？**
能，但 `file://` 下有些功能会受限。建议统一用 VS Code 的 Live Server，地址是 `http://127.0.0.1:5500`。

**Q：玩家看源码不就看到答案了？**
会。所有前端游戏都这样。你不做"看源码"类谜题，就不用管。

**Q：30 页是不是太多了？**
是。先做 8 页能玩通的，验证线索链和引导，再扩。

**Q：四个人都必须会 Git 吗？**
只要会三个按钮：Pull、Commit、Push。十分钟能学会。

**Q：需要买域名吗？**
不需要。`github.io` 的地址够用。

**Q：图片放哪？**
公共图 `assets/img/common/`，页面专属图放 `assets/img/<页面名>/`。

**Q：改了页面多久生效？**
Push 之后 1 分钟左右。

**Q：玩家进度丢了怎么办？**
首页放"重置进度"，再加一个不对外链接的 `debug.html`，能直接发线索。

**Q：中文乱码？**
所有文件保存为 UTF-8。VS Code 右下角可以看和改。

**Q：画布页怎么做才能不变形？**
外层固定宽高比（比如 16:9），里面的元素用百分比定位；整块随窗口缩放，字用 `clamp()` 限制最小最大值。

## 附录 A 命名约定

| 类型 | 规则 | 例子 |
|---|---|---|
| 文件夹 | 英文小写 + 连字符 | `weibo`、`post-detail` |
| HTML 文件 | 英文小写 + 连字符 | `post-01.html` |
| 图片 | 页面名-序号 | `weibo-photo-01.webp` |
| CSS 类名 | 小写 + 连字符 | `.post-card`、`.comment-list` |
| 交互元素 | `data-` 属性 | `data-clue="c01"`、`data-action="open-profile"` |
| 线索 ID | `c` + 两位数字 | `c01`、`c02` |
| 旗标 | 动词 + 名词 | `seen_post_01`、`has_key` |

**元素的名字一旦定下，人不要改，只让 AI 改。** 逻辑脚本靠名字找元素。

## 附录 C 如果决定全部用固定画布

如果你最后还是想"每一页都像 PPT"，可以，但要接受这些代价：

1. 所有页面统一 1600×900，用一个外层容器整体缩放。
2. 所有文字放在固定框里，写之前先估算字数；超了就压住别的东西。
3. 信息流页面要单独做一个"内部滚动区"，滚动条出现在画布里，不是浏览器上。
4. 窄窗口下整体缩小，字会变小；手机横屏勉强能看，竖屏基本不可用。
5. 改一句话可能要重新调位置，30 页的维护量会明显上升。

做法：

- 每页一个 `stage` 容器，固定 1600×900，用 CSS `transform: scale()` 按窗口比例缩放并居中。
- 元素用百分比或像素绝对定位。
- 文字块设固定宽高，超出隐藏或缩小字号。
- 页头页脚也放在画布里，不要用流式。

**不推荐**把信息流、文章、聊天这类内容页做成画布。如果只把封面、现场、结局做成画布，其余流式，就是本手册第 1.3 节的方案，维护成本最低。
